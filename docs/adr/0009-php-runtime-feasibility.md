# ADR-0009: PHP runtime feasibility (v0.4 precondition)

- Status: Accepted for v0.4 — satisfies `docs/ROADMAP.md`'s explicit precondition and `docs/SECURITY.md`'s "approve an ADR covering runtime origin/build reproducibility, iOS execution constraints, extension allowlist, filesystem restrictions, process/shell-related functions, resource limits and remote error behavior" requirement.
- Date: 2026-09-18

## Context
`docs/MASTER-SPEC.md` §3.7 and `docs/ROADMAP.md`'s v0.4 goal both call for serving self-contained PHP applications, particularly SQLite-backed ones — index.php routing, request/response mapping, sessions, PDO. There is no system PHP on iOS (no shell, no `/usr/bin/php`, no dynamic loading of a system-provided runtime); the only way to run PHP at all is to embed an interpreter directly into iServe's own binary.

This is a fundamentally different risk class from everything shipped so far. Every prior ADR in this project (0001–0008) governs *serving already-existing files/requests* through code this project owns end to end. PHP execution means iServe would run **arbitrary, user-supplied, Turing-complete code** against the selected folder, on every request, inside the app's own process. That's not a small addition to `StaticFileHandler` — it's a new subsystem with its own threat model, and `docs/SECURITY.md` is explicit that it needs its own sign-off before a line of integration code is written.

### Is this actually feasible on iOS at all?
Yes, with real, current prior art (checked live, not from training-data memory, since this needs to be accurate as of 2026):
- PHP itself ships an **embed SAPI** (`sapi/embed` in `php-src`, `./configure --enable-embed`) — built exactly for hosting the interpreter inside another application as a library, not a standalone binary. This is the same mechanism every project below uses.
- **NativePHP for Mobile** ships PHP 8.4 built via the embed SAPI, cross-compiled for iOS device and simulator (arm64), thread-safe, and is a maintained, shipping product — the strongest evidence this is viable in App Store apps today, not just a proof of concept.
- Smaller/independent projects (`makalin/php-ios`, `phpnitro`'s iOS branch, `rsky/iphp`) show the same pattern: cross-compile `php-src` for `arm64-apple-ios`/`arm64-apple-ios-simulator`, produce a static `libphp.a`/XCFramework, link it into the app target, drive it from Swift/Objective-C.
- None of this involves downloading or fetching remote executable code — the interpreter is compiled into the signed app binary, and it only ever executes `.php` files already inside the user's selected, on-device folder (the same trust boundary `SecurePathResolver` already enforces for every other file this app serves). That keeps it clear of App Review Guideline 2.5.2 (no remotely-fetched code that changes app behavior) the same way apps like a-Shell/Pythonista/Working Copy already ship embedded interpreters (Lua/Python/Git) today.

So: feasible, with real prior art, but a genuinely large, security-sensitive subsystem to build and maintain ourselves — not a routine feature addition. Sources: [php-ios](https://github.com/makalin/php-ios), [NativePHP Mobile embedded-PHP architecture](https://nativephp.com/docs/mobile/4/architecture/embedded-php), [php-src embed SAPI](https://github.com/php/php-src/blob/master/sapi/embed/README.md), [phpnitro iOS embed-SAPI PR](https://github.com/phpnitro/phpnitro/pull/122), [rsky/iphp](https://github.com/rsky/iphp).

## Decision (proposed)

### Runtime origin & build reproducibility
Build `libphp` ourselves, from the **official upstream `php/php-src`**, pinned to tag **`php-8.4.2`** — never a third-party's prebuilt binary, and never a fork. This matches this project's existing posture toward its two current third-party dependencies (ZIPFoundation/SWCompression, both pulled via SPM from their own upstream repos, never vendored as binaries). A new, dedicated CI workflow (`.github/workflows/php-embed.yml`, kept separate from `ios.yml` — see below) cross-compiles `libphp.a` for `arm64-apple-ios` (device) and `arm64-apple-ios-simulator`, from a checked-in, documented `./configure` flag set — reproducible from source on every run, not a binary blob committed to the repo. `docs/DEVELOPMENT.md`'s "CI is the only real signal" posture extends naturally to this: there is no local Swift compiler *or* PHP cross-toolchain in this environment either.

Kept in its own workflow file rather than added to `ios.yml`: cross-compiling PHP's embed SAPI has known-fragile spots even on a plain native macOS build (long-standing upstream `php-src` issues around exactly this), so every job in it runs with `continue-on-error: true` and no dependency from the app's own build/test/release jobs — a red X here must never block an unrelated PR to the app itself. The plan is intentionally incremental and CI-observed rather than written blind in one pass, split into separate jobs that each isolate exactly one variable: (1) does `./configure`+`make` produce a `libphp.a` at all when cross-compiled against the iOS device SDK; (2) does the embed SAPI's own C API (`php_embed_init`/`zend_eval_string`/`php_embed_shutdown`) actually work, proven by building the *same* SAPI natively for macOS (build host == target, so the result can just be run directly, no iOS-specific risk mixed in) and executing a real "hello from embed SAPI" smoke test; (3) the iOS Simulator target, which — unlike a device binary — runs as an ordinary native process on the very same Apple Silicon CI runner and can be executed there via `xcrun simctl spawn` against a booted simulator, closing the gap between (1) and (2) by proving cross-compiled *and* runnable at once; (4) a device-target link smoke test (build-only — a device binary targets real iPhone silicon, not this runner's own macOS kernel, so it can never execute here regardless of how it's invoked; verifying on a real device stays a manual step, same as this project's existing manual on-device verification for anything the CI runner itself can't do).

### iOS execution constraints
- Embed SAPI runs **in-process**, synchronously, one request at a time. iServe's existing concurrency model gives every connection its own actor running concurrently; PHP's interpreter globals are not safe to touch from more than one place at once even in a thread-safe (ZTS) build used this way. v0.4 serializes **all** PHP execution through one new actor (a "PHP worker") — one script runs to completion before the next starts, regardless of how many HTTP connections are open concurrently. This is a deliberate v0.4 scope limit (throughput over correctness would be the wrong trade for a first cut), not a permanent architecture; documented as a revisit trigger below.
- No dynamic extension loading (`enable_dl=0`, `dl()` unavailable) — every extension is statically compiled into the one `libphp.a`, decided at iServe's own build time, not by a script's `php.ini`.

### Extension allowlist
Statically compiled in: `pdo_sqlite`/`sqlite3` (the explicit roadmap deliverable), `session` (file-based, confined under the served root — see filesystem restrictions), `json`, `mbstring`, `hash`, `filter`. Explicitly **excluded** from v0.4: `curl`/sockets (a PHP script making outbound network requests is a materially different threat than "serve local files" — the device would originate traffic a person never asked for), `FFI` (arbitrary native code execution, defeats every other restriction here), `GD`/`imagick` (real value, meaningfully larger build and attack surface, deferred rather than justified for a first cut). Anything not on this list simply isn't compiled in — a script calling it gets PHP's own "undefined function" error, not a security boundary to enforce at runtime.

### Filesystem restrictions
PHP's `open_basedir` is set, per request, to the exact resolved root `SecurePathResolver` already computed for that session/mount — a script can `fopen()`/`include()`/`require()` nothing outside what the HTTP layer itself could already reach. `include_path` is cleared (no implicit search outside the served root). Session files (`session.save_path`) live under the app's own container, never under the served folder, so a PHP session can't be listed/downloaded as if it were served content.

### Process/shell-related functions
`disable_functions` covers `exec,shell_exec,system,popen,proc_open,proc_close,pcntl_*,posix_*,dl` unconditionally, regardless of build configuration. Most of these would already fail hard under iOS's sandbox (no `fork`/`exec` at all) — disabling them explicitly turns an undefined, possibly-crashing failure mode into a clean, expected PHP error, and closes the door on any of them ever working after a future PHP version changes what's technically possible in-sandbox.

### Resource limits
Bounded the same way every other part of this server already is bounded (`ServerCore/HTTPServer.swift`'s `HTTPServerLimits`, extended with PHP-specific fields rather than a separate mechanism): `max_execution_time` (a low double-digit number of seconds — a hung script must not be able to hold a connection/worker open indefinitely, mirroring the existing idle/lifetime connection timeouts), `memory_limit` (tuned well below what would risk the OS jetsam-killing the whole app under memory pressure — this app runs alongside everything else on someone's phone), and POST/upload sizes reusing the existing `maxUploadBytes`-style bound rather than introducing a second cap that could disagree with it.

### Remote error behavior
`display_errors` is **always off** in the embedded SAPI, unconditionally — a remote client never sees a PHP stack trace, file path, or source fragment, matching every other error path in this project (`docs/SECURITY.md`'s existing "never leak local paths" rule, already enforced for `ServerCoordinator`'s own start-failure messages). An uncaught fatal/exception becomes a generic `500`; the real error is captured into the roadmap's own "PHP diagnostics console" deliverable (on-device only, in the app's UI) and optionally `RequestLog`, never the HTTP response body.

### Capability gating
PHP execution is a new, explicit, session-level toggle (`ServerCoordinator`-level, analogous to `requiresPassword`) — off by default, per `docs/SECURITY.md`'s standing "explicit capability, never implied by selecting a folder" rule. It is **orthogonal to `ServerProfile`**, not a fifth profile: any profile that already allows directory listing can additionally allow PHP execution of `.php` files it would otherwise have served as plain static (unparsed) text, exactly as `docs/MASTER-SPEC.md` §3.1 already frames it ("later `index.php` when PHP is enabled"). A `.php` file is never executed when this toggle is off, regardless of profile — it round-trips as an ordinary static file, matching today's behavior exactly, so nothing about existing sessions changes until someone opts in.

### Code-signing / distribution
`libphp.a` is a static library linked into the app target at build time — the entire binary, PHP included, is signed as one unit by the existing app signing/export pipeline (`.github/workflows/ios.yml`'s `ipa` job), with no new signing step and no dynamically-loaded component at runtime. The known cost: app binary size grows substantially (a statically-linked PHP interpreter with even a minimal extension set is commonly tens of MB) — acceptable for what this unlocks, but worth surfacing to whoever approves this ADR, since it's a permanent, user-visible download-size cost, not a build-time-only one.

## Consequences

### Positive
- Real, dynamic self-contained web apps (the roadmap's actual goal) become servable, not just static files — the single biggest capability gap between iServe and a "real" file/web server.
- Grounded in a proven approach (embed SAPI, static linking, no remote code fetch) with multiple independent, current examples already shipping this exact pattern on iOS.
- The capability-gating/filesystem-restriction/error-sanitization design reuses this project's own existing patterns end to end (`ServerProfile`-style opt-in, `SecurePathResolver`-anchored containment, sanitized remote errors) rather than inventing a parallel security model just for PHP.

### Costs
- A new, ongoing maintenance burden this project didn't previously have: PHP's own security patch cadence now becomes iServe's problem too, since the interpreter is vendored and built by this project, not provided by the OS. A future ADR/process for tracking and re-pinning PHP versions is needed before this ships, not just at initial launch.
- Meaningful app binary size increase, and a new, nontrivial CI job (cross-compiling PHP from source) that lengthens build times and is a new thing that can break independently of the Swift app code.
- A materially larger security surface than anything shipped in v0.1–v0.3: even with every restriction above, "execute arbitrary code against a selected folder" is categorically riskier than "serve/list/upload files in a selected folder," and deserves its own dedicated test suite (the roadmap's own "compatibility/security test suite" deliverable) before this is considered release-ready, not just unit tests alongside the rest of `Tests/iServeTests`.
- Serializing all PHP execution through one worker actor means a slow PHP script blocks every *other* PHP request behind it (though never non-PHP static/WebDAV traffic, which stays on its own per-connection actors) — a real, user-visible throughput ceiling for anyone running a busier PHP app, accepted here as a deliberate v0.4 scope limit.

## Implementation addendum (Swift/C bridge, `PHP/Bridge/`)
Three corrections found while building `PHP/Bridge/iserve_php_bridge.c` against PHP's real `sapi/embed`/`main/SAPI.h` source (checked live against the pinned `php-8.4.2` tag, not from memory) and worth recording here rather than letting the ADR's prose drift from what actually ships:

- **`disable_functions` cannot glob.** It only accepts an exact, literal, comma-separated function-name list — there is no `pcntl_*`/`posix_*` prefix support, so the "Process/shell-related functions" section's phrasing was imprecise. Those two extensions are kept out of the running entirely (they were never in the extension allowlist to begin with), so nothing calling into them can exist as a compiled function in the first place — `disable_functions` only needed to name the `ext/standard`-resident functions that *are* always compiled in regardless of the allowlist: `exec,shell_exec,system,popen,proc_open,proc_close,dl`.
- **`open_basedir`, `display_errors`, and `max_execution_time` are all `PHP_INI_ALL`** — modifiable by the script itself via `ini_set()`/`set_time_limit()` at runtime, not just by the embedding host. Without also disabling the setter functions, a script could widen or remove any of these three restrictions on itself. `ini_set`, `ini_alter` (its legacy alias), and `set_time_limit` are therefore added to `disable_functions` alongside the process/shell functions above.
- **`allow_url_fopen`/`allow_url_include` are forced off.** Excluding `curl` from the extension allowlist doesn't by itself stop a script from reaching a remote URL — PHP's own stream wrappers let `fopen()`/`include()`/`require()` open `http://`/`https://` URLs independent of curl. Both directives are set to `0` so that door stays shut too, matching this ADR's existing "no remotely-fetched code" framing for the app binary itself, extended to what a running script can do.

`open_basedir` is narrowed per request (`zend_alter_ini_entry_chars(..., PHP_INI_STAGE_ACTIVATE)`, right after `php_request_startup()`) to each request's own resolved root, and PHP's own ini-stage-revert mechanism resets it automatically at that request's shutdown — confirmed from source, not assumed, since this project's single persistent PHP worker runs many requests per process rather than the one-shot-per-process model `sapi/embed`'s own convenience macros (`PHP_EMBED_START_BLOCK`/`_END_BLOCK`) are built for; the bridge reimplements the startup/per-request/shutdown split by hand for exactly that reason (see the file-level comment in `iserve_php_bridge.c`).

## Revisit triggers
Reconsider the single-worker serialization if a real self-contained app's usage pattern needs concurrent PHP requests to feel responsive (would need either a thread-safe/ZTS build with per-request interpreter contexts, or a small pool of worker actors — a larger change, not a tweak). Reconsider the extension allowlist if a specific, real target application needs `curl`/GD/imagick badly enough to justify the added attack surface and build complexity — each addition should be its own small ADR amendment, not a silent expansion. Revisit PHP version pinning on every upstream PHP security release, not just opportunistically.

**Already triggered once**: a real need for PHP scripts to reach the internet (an RSS feed, a third-party API, a remotely-hosted asset — for locally-tested, still-in-development sites, not just fully self-contained ones) has been named. See `docs/adr/0010-php-outbound-networking.md` — a stub naming the open questions this needs resolved before it's implemented, deliberately left `Proposed` rather than folded into this ADR's already-accepted scope. `allow_url_fopen`/`allow_url_include` stay off and no network-capable extension is compiled in until that ADR is actually accepted.
