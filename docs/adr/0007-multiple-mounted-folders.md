# ADR-0007: Optional multiple mounted folders via a secure per-mount namespace

- Status: Accepted for v0.3
- Date: 2026-09-17

## Context
`docs/ROADMAP.md`'s last remaining v0.3 deliverable is "Optional multiple mounted folders after secure namespace design." Until now `FileSystem/FolderRootManager.swift` manages exactly one selected root, and every HTTP request resolves through exactly one `FileSystem/SecurePathResolver.swift` rooted there. Supporting more than one shared folder in the same session means answering, concretely, the "secure namespace design" the roadmap names as a precondition: how does one HTTP request-target unambiguously pick one folder's own root, with no way for a request meant for one mount to be satisfied by, or escape into, another.

This must stay **optional** in the literal sense: a session with exactly one folder selected (every existing session, and the common case going forward) must behave exactly as it does today — same root serving, same `/` behavior, same tests passing unchanged. Namespacing is a cost that should only appear once a second folder actually exists.

## Decision
**Namespace scheme.** Each folder beyond the first (the already-existing "selected folder," still managed exactly as before) is an *additional mount*: a name (a single, validated path component — same rules `SecurePathResolver`'s own component validation already applies: non-empty, not `.`/`..`, no `/`/`\`, no control characters) plus its own bookmark, resolved to its own root. A request path is dispatched by its **first path component**: `/<mount-name>/...` resolves entirely within that mount's own `SecurePathResolver(root:)` — a completely separate resolver instance per mount, so one mount's containment check can never be satisfied by another mount's filesystem tree. The primary (first-selected) folder keeps serving at the *bare* root (`/...`, no name segment) for backward compatibility, exactly as before.

**`/` never changes meaning — additional mounts are purely additive.** `Handlers/MountRouter.swift` is the new top-level router `LiveServerService` builds instead of a bare `StaticFileHandler`. For *every* request, it checks only whether the target's first path component exactly matches a known additional mount's name; if not — which includes every request when there are zero additional mounts, and `/` itself always, since a bare root has no first component to match — the request passes to the primary folder's own `StaticFileHandler` completely unchanged (the same `HTTPRequest` value, not even reconstructed). There is deliberately no generated "index of mounts" page at `/`: the primary keeps meaning exactly what it always has, with zero conditional behavior based on how many mounts exist. Discovery of additional mounts' URLs is the app UI's job (`App/ServerDashboard.swift` lists each one's full address next to the primary's, same as it already does for alternate network interfaces), not a new piece of server-generated HTML. This is the same "capability the user never turned on doesn't change anything" posture `docs/SECURITY.md` already applies elsewhere (uploads, WebDAV writes, Website Read Only's listing suppression) — here it's "a feature the user never used doesn't change anything," including for anyone probing the same server: a single-folder session presents no different an attack surface than it did before this ADR.

A named mount takes priority over a same-named top-level entry inside the primary folder: if a mount is named `Photos` and the primary folder also happens to contain a top-level item called `Photos`, requests to `/Photos/...` reach the mount, and that entry inside the primary becomes unreachable over HTTP for as long as the mount exists by that name (still reachable locally through the in-app file manager, which only ever browses the primary folder — see below). A documented shadowing rule, not a security issue: nothing escapes either root's own containment.

A bare mount reference with no trailing slash (`GET /photos`, not `/photos/`) gets the same `301` redirect to the slash-terminated form `StaticFileHandler.route(_:)` already gives the primary's own directories, so a mount's relative links resolve correctly. Every other `HTTPRouter` requirement (`PROPFIND`/`MKCOL`/`DELETE`/upload and ZIP authorization) has no such redirect concept to begin with (`docs/adr/0004-webdav-read-operations.md` already established `PROPFIND` doesn't redirect), so a bare mount reference there is treated as that mount's own root directly.

**Additional mounts are read/download only, regardless of the active `ServerProfile`.** A `MountRouter`-owned mount's `StaticFileHandler` is always constructed with `allowUploads: false` and `allowWebDAVWrites: false`, no matter what profile the session is running under — only `allowDirectoryListing` (browsing) follows the profile, same as the primary. Extending uploads/WebDAV writes to every mount independently would mean deciding whether capabilities are per-session or per-mount, a materially bigger question (per-mount profiles, per-mount password protection, ...) this ADR does not attempt. A person who wants to *write* to a folder still adds it as the one primary selected folder; additional mounts are for sharing more read-only content alongside it. `Handlers/DirectoryListingRenderer.swift`'s ZIP-download form remains available on every mount, same as today, since it was never profile-gated to begin with.

**`MOVE`/`COPY` never cross mounts.** `Handlers/MountRouter.swift` resolves the `Destination` header's own path the same way as the source path (by its own first component; the small `Destination`-header-to-path parser `StaticFileHandler` already had is now `Handlers/WebDAVDestinationHeaderParser.swift`, shared by both rather than duplicated). If the two resolve to different mounts (including "primary" vs. any named one), the request is refused with `409 Conflict` before either mount's own handler is asked to do anything. Since additional mounts are read-only anyway, this only matters for moving/copying *within* the primary mount, which already works exactly as before (no cross-mount question ever reaches `StaticFileHandler` itself).

**The in-app file manager (`App/FileManagerScreen.swift`) only ever browses the primary folder, unchanged.** It already holds its own independent `beginAccess()`/`endAccess(_:)` pair against `FolderRootManager` — reentrant with a running server's own access — and nothing about that changes here; browsing/editing additional mounts locally is out of scope for this increment, same as their write capability over HTTP.

**Mount name collisions are resolved automatically, deterministically, at add-time.** `FileSystem/FolderRootManager.swift` derives a candidate name from the folder's own last path component, sanitizes it against the same component-validation rules, and appends `-2`, `-3`, ... until it no longer collides with the primary folder's name or any existing additional mount's name. A person adding a folder never has to think about naming unless two folders happen to share a name.

**Bookmark storage.** A new `FileSystem/FolderAccess.swift` protocol, `MountBookmarkStore`, persists an ordered `[(name: String, bookmark: Data)]` list (JSON-encoded into one `UserDefaults` value, mirroring `UserDefaultsFolderBookmarkStore`'s single-bookmark shape) — entirely separate from the primary folder's existing bookmark key, so this ADR changes nothing about how the primary folder is stored or resolved.

**Scoped access.** `ServerCore/LiveServerService.swift`'s `start(profile:credentials:)` now acquires scoped access for the primary folder (as before) *and* every currently-resolvable additional mount, and releases all of them together on `stop()` — the same reference-counted, per-URL `FolderAccess.startAccessing`/`stopAccessing` primitive already used for one folder, just called once per mount. A mount whose bookmark fails to resolve at start time is silently skipped for that session (not fatal to starting) rather than blocking the whole server from starting over one bad mount; it stays visible in the UI so the person can remove or fix it.

## Consequences
### Positive
- Exactly one behavior change is possible for the overwhelmingly common single-folder case: none. Every existing test, every existing profile/auth/WebDAV/ZIP feature keeps working against the primary mount completely unchanged, because `MountRouter` with zero additional mounts is a transparent pass-through.
- Per-mount resolver isolation means the traversal/symlink-escape protections `SecurePathResolver` already provides apply per mount with no new shared state to get wrong — there is no single resolver instance whose root could be confused between mounts.
- Mount naming needs no user attention in the common case (no two folders sharing a name), while still being deterministic and conflict-free when it does happen.

### Costs
- Additional mounts cannot be written to, uploaded to, or WebDAV-managed in this increment, regardless of `ServerProfile.fullAccess`/`.fileDrop` — a real capability gap versus a hypothetical "any mount can do anything the profile allows" design, accepted to avoid a much larger per-mount-capability model.
- `MountRouter` must implement every `HTTPRouter` requirement as a name-dispatching wrapper, which is mechanical but broadens the "dispatch a request" surface a security reviewer needs to read; each one is a thin, uniform "strip the name, delegate" shape rather than distinct logic, to keep that review cheap.
- `MOVE`/`COPY` across mounts is a hard `409`, not a "copy the bytes across mounts" fallback some WebDAV clients might expect — acceptable since additional mounts are read-only anyway (a write attempting to *originate* a copy into one would already be refused for that reason first).
- A stale/unavailable additional mount is silently skipped when starting the server rather than surfaced as a hard failure — consistent with "one bad mount shouldn't block everything else," but means a person could serve fewer mounts than they expect without an explicit per-session error, only what the mount-management UI already shows.

## Revisit triggers
Reconsider read-only-only additional mounts if a real need for per-mount write capability shows up — that needs its own ADR (per-mount profiles or an explicit "which mounts are writable" list). Reconsider the cross-mount `MOVE`/`COPY` refusal only alongside that same revisit, since it stops mattering until mounts can be written to at all.
