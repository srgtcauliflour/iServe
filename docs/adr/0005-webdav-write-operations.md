# ADR-0005: Authorized WebDAV write operations (MKCOL/PUT/DELETE/MOVE/COPY)

- Status: Accepted for v0.3 (LOCK/UNLOCK explicitly out of scope — see Consequences)
- Date: 2026-09-17

## Context
`docs/adr/0004-webdav-read-operations.md` shipped `OPTIONS`/`PROPFIND` and explicitly deferred "authorized write operations" to a separate ADR once `ServerProfile.fullAccess` (`docs/adr/0003-capability-based-server-profiles.md`) had something real to do. Until now `.fullAccess` was defined but behaviorally identical to `.fileDrop` — this ADR is what finally distinguishes them.

`docs/MASTER-SPEC.md` §4 describes Full Access as "explicit advanced profile enabling authorized WebDAV/file-management writes," and §3.6 as "controlled writes (upload/create/rename/move/copy/delete) according to server permissions." A WebDAV client (Finder "Connect to Server", Cyberduck, Documents by Readdle, `davfs2`, `curl --upload-file`, etc.) expects five methods to make a mount usable for editing: `MKCOL` (create a directory), `PUT` (create or overwrite a file), `DELETE`, `MOVE`, and `COPY` (the latter two via a `Destination` header).

**Note on `AGENTS.md`'s module boundaries.** `AGENTS.md`'s "Initial module boundaries" sketches a standalone `WebDAV/` folder. ADR-0004 already departed from that (silently, in retrospect) by adding WebDAV read support directly to `ServerCore/HTTPRouter.swift`/`Handlers/StaticFileHandler.swift` rather than a new module; this ADR continues that choice for writes rather than splitting the two halves of one protocol across two locations. The reason: everything WebDAV needs here is either a couple of new `HTTPRouter` requirements (dispatched by `HTTPConnection` exactly like every other method) or logic that belongs next to the identical GET/upload logic it mirrors (`routeWebDAVMkcol` next to `route(_:)`'s directory handling, `authorizeWebDAVPut` next to `authorizeUploadedFile`). A separate top-level module would only be justified by protocol-specific state or a boundary genuinely worth isolating — WebDAV here is a thin, per-method extension of the one request pipeline already serving GET/HEAD/POST, not a distinct subsystem. `Handlers/WebDAVResponseBuilder.swift` is the one new file, and it already sits beside its HTML equivalent, `DirectoryListingRenderer`.

## Decision
Add a fourth `ServerProfile` capability, `allowsWebDAVWrites`, true only for `.fullAccess` — now added to `ServerProfile.selectable` since it finally has a distinct effect. `Handlers/StaticFileHandler.swift` gains a matching `allowWebDAVWrites: Bool = false` property. Every write route refuses with `404` when this is off — the same "hide the capability, don't reveal a resource's existence separately from whether the capability is enabled" convention `authorizeUpload`/`allowDirectoryListing` already use, kept consistent here rather than switching to `403` for writes specifically.

**PUT overwrites; uploads still don't.** A conformant WebDAV `PUT` is expected to create-or-replace — refusing to overwrite (the browser-upload posture, `docs/SECURITY.md`'s "never silently overwrite") would make WebDAV useless for the single most common write workflow, editing an existing file in place. Enabling Full Access is the explicit, one-time opt-in that accepts this; `.fileDrop` (uploads without WebDAV writes) keeps the no-overwrite posture unchanged. To avoid a worse failure mode than a plain upload's "delete the partial file on failure" — an interrupted PUT corrupting a file that already existed and was fine — `PUT` writes to a hidden temporary sibling file (`.iserve-put-<uuid>.tmp`, same directory, so the final step is an atomic rename/replace on the same volume) and only replaces the real destination once every declared body byte has arrived intact. A failure at any point deletes the temporary file and leaves an existing destination completely untouched. This is a deliberate divergence from the upload path's direct-write-with-delete-on-failure (acceptable there specifically because overwrite was never allowed, so there was nothing at that path worth protecting).

**Never touch the served root itself.** `DELETE`, and `MOVE`/`COPY` as a source or destination, all refuse (`403`) if the resolved path is exactly `resolver.root` — deleting or overwriting the folder the user selected would corrupt `FolderRootManager`'s security-scoped access out from under the running session. `MKCOL` and `PUT` can never target root by construction (root always already exists as a directory, so `MKCOL` there is `405` and `PUT` there is refused as "target is an existing directory").

**`MOVE`/`COPY` refuse moving/copying a directory into its own subtree** (`409 Conflict`) — otherwise a client could ask this server to recreate a resource inside itself, which has no sound filesystem semantics (infinite nesting or a broken half-move). The `Destination` header is parsed via `URLComponents.percentEncodedPath` specifically (never `URL.path`, which silently percent-*decodes* — using it here would resolve a subtly different, wrongly-decoded path than the one the client meant, exactly the kind of mismatch `docs/SECURITY.md`'s single-decode discipline exists to prevent).

**Two RFC 4918 conveniences this server does not implement**, both simplifications in the same spirit as ADR-0004's:
- A missing intermediate parent collapses into this server's ordinary `404` (`SecurePathResolver`'s uniform `.notFound` mapping, shared with every other route) rather than RFC 4918 §9.3.1's specific `409 Conflict` for `MKCOL`. A well-behaved client reacts to either the same way (create the parent first).
- `MKCOL` never auto-creates intermediate directories (`withIntermediateDirectories: false`) — this is not a relaxation but the *correct* RFC behavior; RFC 4918 explicitly forbids `MKCOL` from creating more than the one requested collection.

## Consequences
### Positive
- Every write route reuses `SecurePathResolver`/`Self.response(for:)`'s existing error mapping rather than inventing parallel path-safety logic.
- The temp-file-plus-atomic-replace `PUT` strategy means an interrupted upload can never corrupt a pre-existing file — strictly safer than what a naive direct-write `PUT` would have given.
- `.fullAccess` finally does something a person can reason about, closing the placeholder ADR-0003 left open.

### Costs
- **No `LOCK`/`UNLOCK`.** Some WebDAV clients (notably older Windows WebClient/mini-redirector behavior, and some macOS Finder write paths) probe for lock support before allowing writes and may refuse to write against a server that never grants one. Implementing even a "fake" always-granted lock is meaningful additional surface (a `Lock-Token`/`opaquelocktoken` response, `If` header handling for `UNLOCK` and conditional requests) deferred until a real client actually needs it — see Revisit triggers. Clients that don't require locking (Cyberduck, `curl --upload-file`, `rclone`, most iOS file-manager apps, `git`) are unaffected.
- Not fully RFC 4918-conformant on the two points named above (missing-parent status code, and — inherited from ADR-0004 — `PROPFIND`'s fixed property set and `Depth: 0/1`-only restriction, both of which still apply here since writes reuse the same read path for existence checks).
- `MOVE`/`COPY`'s `Overwrite: F` support is a boolean gate (`412 Precondition Failed` when the destination exists and the client asked not to overwrite) — no partial/best-effort semantics beyond that, matching RFC 4918's own binary treatment of the header.

## Revisit triggers
Add `LOCK`/`UNLOCK` only once a specific, justified client actually fails without it — implementing speculative lock support with no real client to validate against risks shipping an untested, security-relevant surface for no proven benefit. Revisit the missing-parent status-code simplification only if a specific client's behavior depends on distinguishing `409` from `404` there.
